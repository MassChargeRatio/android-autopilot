# AndroidAutopilot 分层架构提案 v6

> 2026-10-29，供外部评审。**本文自包含**，不看仓库也能评审。
> v6 相对 v5 的三处变更（由项目方拍板）：
> ① `report` 定名 **`daily_report`**；
> ② **不再强制 `collect` 的执行顺序**——它是兜底，不承担主效果；顺序约束换成**幂等约束**（§7）；
> ③ 拒绝在 step 上加 `vision` 字段，视觉策略只存在于 `target.vision`（避免又一次同义双轨，§5.7）。
>
> 规模基线：34 个 App / 99 条例程 / 389 个顶层步骤（含分支展开 542）/ 452 测试全绿 / 覆盖率 99/99。

---

## 0 一句话

把"步骤类型"这个混乱枚举拆成**三个正交维度**（动作 / 控制流 / 组合宏）；
把"意图→例程"的映射表**删掉**（名字相等即通，无重定向）；
意图收敛到 7 个**可判定终态**的用户目标。

---

## 1 问题诊断（实测）

### 1.1 `type` 一词双义

```yaml
- type: click_first        # 顶层 type = 做什么
  candidates:
  - type: text             # 候选 type = 怎么找
```

顶层没有 `text`，候选里没有 `click_first`——同一字段名承载两个维度。

### 1.2 四个维度压进一个枚举

19 个 type 里混着：动作（`click_text`/`swipe`）、定位方式（混在动作里）、控制流（`any_of`）、
业务宏（`dismiss_popups`）、时序（`wait`/`think`）、断言（`ensure`/`reward`）。

`click_text` 与 `click_point` 在"动作"维度上**都是 click**，差别只在"怎么找"。

### 1.3 意图映射表 97% 是噪音

`intent_map` 共 63 条，**61 条是恒等映射**（`sign: sign`），真正起作用的只有 2 条。

### 1.4 返回值语义不一致（已修）

`_run_kind` 原统一 `None → True`，使"没做判断"与"判断通过"同义。已按返回值契约分 9 类修复。

## 2 架构总览

```
intent（7 个，平级，无映射表）
  sign · reserve · daily_report · chest · withdraw · watch · collect
    │  名字相等即匹配；没有同名 routine = 不支持（不自动降级）
    ▼
routine（一个 App 支持几个意图，就写几条链）
    ▼
step（三选一：action | flow | macro）
    ▼
执行器（uiautomator2 / adb）
```

概念 4 个：`intent → routine → step → target`。**没有 route、没有 intent_map、没有例外表。**

## 3 七个 intent

| intent | 中文 | 定义 | 终态判定 | 现有条数 |
|---|---|---|---|---|
| `sign` | 签到 | 点签到按钮 | 签到类点击凭据，或重开 App 见「已连续签到 N 天」 | 28 |
| `reserve` | 预约 | 预约下一场 | 见「已预约，xx 后可领取」 | 1 |
| `daily_report` | 领日报 | 领每日日报奖励 | 日报页显示已领取 | **0（待实现）** |
| `chest` | 领宝箱 | 开具名奖励容器（宝箱/红包/翻牌/抽奖） | 宝箱消失或变倒计时 | 10（原 bonus 9 + gift 1） |
| `withdraw` | 提现 | **走到提现页、读到余额为止；提交由人执行** | 停在提交前 → 报「待人工」 | 22 |
| `watch` | 看视频 | 刷视频赚金币 | 内容页停留达标 + 任务状态变化 | 18 |
| `collect` | 扫任务页 | 扫一遍页面，点掉**不属于其它 6 个意图**的散落可领项 | 结构判定：页面上无剩余「领取」文案 | 18 |

### 3.1 `chest` 为什么单列

1. **悬浮控件，跨页存在**，不依附任何页面结构；
2. **有独立终态**（开完消失/倒计时），`collect` 只有"扫干净了"；
3. **识别靠图标 / `contentDescription` / 模板图**，`collect` 靠页面文案——定位策略不同。

### 3.2 `withdraw` 的 scope 与命名张力

它的实际动作是"进提现页、读余额、停在提交前"，不点"确认提现"（资金红线）。
名字叫 `withdraw`（提现）而动作只到"提交前"，是名实不完全一致——**这是有意的**：
用户的目标确实是提现，只是自动化止步于人的确认点。因此它不叫 `balance`，而是在报告里
用第四态「待人工」表达"链跑完了，等你去点最后一下"。

### 3.3 `collect` 的定位与唯一硬规则

`collect` 是**兜底**，不承担主要效果——它只负责"把前面动作漏下的零碎奖励扫一遍"。
因此：

- **唯一硬规则**：只收不属于其它 6 个意图的动作（不允许重复实现 sign/chest/daily_report，
  否则两条链点同一批按钮，报告无法归因）；
- **不约束执行顺序**（项目方决定）。顺序自由的前提是**幂等**，见 §7。

`collect` 的终态是**结构判定**（扫完后页面上无剩余「领取/待领取」文案），不是点击证据。
这不是"更难验证"，是"验证方式本来就不同"——它没有单一目标按钮。

## 4 routine 层

### 4.1 命名规则

> **routine 名必须等于 intent 名。**

解析一行：

```python
return intent if intent in routines else None
```

### 4.2 不支持时不降级

用户说「抖音火山版签到」，该 App 只有 `reserve` → 正确行为是回话
「该 App 不支持签到，可用：预约、观看、提现」，**不是偷偷跑预约再在报告里写"签到"**。
自动降级就是路由表换皮。

### 4.3 routine 的值永远是"步骤数组"

```yaml
routines:
  sign: [ ... ]      # 一条链
  chest: [ ... ]
```

**不引入 `{exclude: [...], steps: [...]}` 这类 dict 形态**——那会让 routine 出现第三种 schema。
`collect` 需要的"排除核心按钮"，已由候选词表按类别隔离保证（见 §6.3），不需要配置字段。

## 5 step 层

### 5.1 action（6 个，动词原形）

| action | 语义 | 返回值契约 |
|---|---|---|
| `click` | 找到元素再点 | `True`=点中 / `False`=未找到 |
| `tap` | 按坐标点（不找） | `True`=落地通过 / `False`=落地失败 / `None`=无可判信号 |
| `swipe` | 滑动 | `True` / 缺坐标抛 `StepError` |
| `press` | 系统键 | `True` / `False` |
| `wait` | 等待（`human: true` = 拟人停顿） | `None`（永远成功） |
| `extract` | 读屏抽数 | `None`（只记录） |

`input` 预留。

### 5.2 flow（2 个）

| flow | 语义 | 别名 |
|---|---|---|
| `first_ok` | 按序试分支，第一组**全部成功**即停 | `any_of`（永久有效） |
| `pick_one` | 随机挑一组 | `random`（永久有效） |

顺序是**功能性**的：只有最后一个分支走视觉兜底，前面的分支是"便宜探测"
（本机 VLM 图像请求常 90s 超时）。

### 5.3 macro（2 个）

| macro | 内部 |
|---|---|
| `dismiss_popups` | 文案 → 关闭 id → 右上角 → BACK，含资金黑名单熔断 |
| `captcha` | 检测滑块 → 缺口识别 → 拟人拖拽 |

宏可含等待与多次尝试；动作只做一件事。

### 5.4 target（仅 `action: click`）

| 字段 | 取值 | 说明 |
|---|---|---|
| `by` | `text` `id` `desc` `image` `vision` | 找法，全部是"按条件找元素" |
| `value` | 选择器值 / 图片路径 / VLM 提示词 | — |
| `pool` | 多候选，按序试 | 原 `click_first.candidates` |
| `search` | `scroll` | 原 `scroll_to` |
| `fallback` | `[x, y]` | 视觉锚点未命中时的坐标兜底 |
| `vision` | `false` | 关闭视觉分支 |

**`coord` 不在 `by` 里**：坐标没有"找"的过程。塞进 `by` 只是把 `click_point`
一肩挑"定位+点击"的耦合从字段层挪进值域层。

### 5.5 step 级属性

| 属性 | 取值 | 说明 |
|---|---|---|
| `on_miss` | `skip`（默认）/ `fail` | 这步没命中怎么办；`flow` 与 `action` 都用它 |
| `expect` | `text_any` / `phash` / `retry` / `settle` | 落地校验；**retry 只在这里** |
| `label` | 任意字符串 | 人类标签，进日志（原 `desc` 双义中的"标签"义） |

### 5.6 三种点击形态

```yaml
# ① 元素点击（188 处）
- action: click
  target: {by: text, pool: [立即打卡, 打卡]}

# ② 视觉锚点 + 坐标兜底（78 处）—— 占原 click_point 的 66%
- action: click
  target: {by: image, value: 领火苗.png, fallback: [0.9, 0.138]}

# ③ 纯坐标（40 处）
- action: tap
  value: [0.5, 0.641]
  expect: {phash: ref.png}
```

**配置味道**：25 处"有图像锚点却 `vision: false`"，锚点永不生效。
v2 里 `by: image` + `vision: false` 自相矛盾，编译层应拒绝并 WARN。

### 5.7 `first_ok` 的分支视觉策略：只改 `target.vision`，不新增 step 级字段

默认规则：`first_ok` **只有最后一个分支**允许走视觉兜底，前面的分支是"便宜探测"
（本机 VLM 请求常 90s 超时）。这条默认是功能性的，但需要能被覆盖。

覆盖方式**只用一个字段**——`target.vision`：

```yaml
- flow: first_ok
  branches:
  - - action: click
      target: {by: image, value: ref.png, vision: true}   # 非末分支，显式开视觉
  - - action: click
      target: {by: text, pool: [立即打卡], vision: false}  # 末分支，显式关视觉
```

**拒绝在 step 上加一个 `vision` 字段**：`target.vision` 已经在表达同一件事，两个位置写同一个开关，
就是 `type` 双义的翻版。视觉是"怎么找"的属性，归 `target`；`tap` / `swipe` 没有 `target`，
它们本来就不涉及视觉定位，不需要这个开关。

## 6 互斥与词表

### 6.1 原则

每个 intent 只负责自己的按钮；`collect` 只收其它 6 个意图之外的散落项。

### 6.2 靠什么保证（不靠运行时状态）

1. **词表按类别隔离**（已有机制）：`candidates.INTENT_TO_CATEGORY` 把行为名映射到词表类别
   （`sign→sign`、`collect→task_center`），`click_first` 自动并入的候选词来自**本类别**，
   所以 `collect` 的池子天然不含签到词。
2. **幂等保证**：每个 routine 首步判终态（§7.1）。顺序自由时，`collect` 先跑也不会把 `sign`
   变成"找不到按钮 → 步骤失败"；已签状态会被终态检查识别，`sign` 直接结束且不记失败。

**不做**：运行时检查 `sign` 是否已跑过（依赖日志/页面状态，脆弱、难测试）。

### 6.3 唯一需要守的纪律

`collect` 的步骤**不得写 `candidates_from: sign`**——那是作者显式把签到词表接进来，
会破坏上面的隔离。编译层应对此报 WARN。

---

## 7 执行顺序：不强制，改用幂等保证

**不再规定全局固定顺序。** 意图按调用方（任务描述）给出的顺序执行，`collect` 可以出现在任意位置。
只有一条顺序约束保留：

- **`withdraw` 单独执行**：资金类，不与其他意图混跑（它止步于提交前，需要人接手）。

### 7.1 顺序自由的代价，以及必须付的补偿：幂等入口

去掉顺序约束后，"先跑 `collect` 再跑 `sign`"是合法调用。此时 `collect` 可能已经把签到按钮点掉了，
`sign` 再去找「签到」会找不到 → 记「步骤失败」→ 报告显示「签到：未确认」——**明明签了，却报没签**。

所以每个 routine 的**第一步必须是终态检查**，而不是直接找按钮：

```yaml
routines:
  sign:
  - action: click
    target: {by: text, pool: [已连续签到, 今日已签到, 已签到]}
    on_miss: skip          # 命中 = 已经签过了，本 routine 直接结束
    label: 终态检查（已签到则跳过）
  - action: click
    target: {by: text, pool: [立即签到, 签到]}
    expect: {text_any: [已连续签到, 已签到]}
```

规则三句话：

1. **先判终态，再找按钮**；
2. 终态命中 → 本 routine 视为"已完成"，**不记失败**（`on_miss: skip` 的语义是"没找到也不算错"，
   但这里更准确的做法是把它写成一条显式断言步，命中即结束）；
3. 终态未命中 → 走正常点击链。

### 7.2 为什么证据仍然可靠

`sign_evidence` 扫的是**一个 App 一次运行的全部日志**，不按 routine 切分。
所以哪怕签到是 `collect` 点掉的，日志里同样有 `点击文本: 签到`，`sign` 依然判「已确认」。
**顺序不影响证据，只影响"步骤失败"信号**——这正是 §7.1 要消掉的东西。

### 7.3 报告归集的前提

若把各意图拆成多次独立运行，则每次运行各自一份日志，证据不会自动合并。
这种情况下汇总层需要按 App 合并当日全部日志再判——这是报告实现的事，不影响架构。

## 8 报告：四态

| 状态 | 判定 | 例 |
|---|---|---|
| **已确认** | 有该意图的点击凭据，或重开 App 见终态 | 签到：已确认 |
| **未确认** | 跑了，但没有点击/终态证据 | 签到：未确认 |
| **不支持** | 该 App 没有这个意图的 routine | 抖音火山版·签到：不支持 |
| **待人工** | 链跑到人的确认点就停 | 提现：待人工 |

现状失真：抖音火山版（只有预约）天天报「签到：未确认」，会训练人忽略整份报告。
改为「签到：不支持 / 预约：已确认」。

---

## 9 硬约束：日志动词不可改

| 形态 | 日志 | 进 `CLICK_LINE`？ |
|---|---|---|
| `click` + `by: text` | `点击文本: X` | ✅ |
| `click` + `by: id` | `点击控件: X` | ✅ |
| `click` + `by: desc` | `点击描述: X` | ✅ |
| `tap` | `点击坐标: (x,y)` | ❌ 故意排除（盲点不是签到凭据） |
| `first_ok` 命中 | `多候选命中并点击: X` | ✅ |

改名只改 YAML 层 key，日志动词一律不动，且**由测试锁住**。

## 10 配置示例

```yaml
name: 抖音火山版
package: com.ss.android.ugc.live
routines:
  # 本 App 没有签到，只有预约；签到判定不会命中，报告显示「不支持」
  reserve:
  - flow: first_ok
    on_miss: skip
    branches:
    - - action: click
        target: {by: desc, value: 领火苗，按钮}
    - - action: tap
        value: [0.9, 0.138]
  - action: click
    target: {by: text, pool: [立即预约领取], expect: {text_any: [已预约]}}
  chest:
  - action: click
    target: {by: text, pool: [开宝箱, 领取]}
  watch:
  - action: click
    target: {by: text, pool: [看视频赚金币, 去完成]}
  - action: wait
    seconds: 30
    label: 停留看视频
  withdraw:
  - action: click
    target: {by: text, value: 提现}
    on_miss: fail
  - action: extract
    pattern: '余额\s*(?P<amount>\d+)\s*元'
    label: 读余额，停在提交前
```

## 11 旧名映射（编译层用）

| 旧名 | 新写法 |
|---|---|
| `behaviors:` | `routines:` |
| `intent_map:` | **删除**（意图名 = routine 名） |
| `type: click` / `click_text` / `click_id` / `click_desc` | `action: click` + `target.by: text` / `id` / `desc` |
| `type: click_first` | `action: click` + `target.pool` |
| `type: click_point`（无视觉锚点，40 处） | `action: tap` |
| `type: click_point`（有 images/vlm_prompt，78 处） | `action: click` + `target: {by: image, fallback: [x,y]}` |
| `type: swipe` / `swipe_natural` | `action: swipe`（+ `natural: true`） |
| `type: back` / `home` | `action: press` + `key` |
| `type: wait` / `think` | `action: wait`（+ `human: true`） |
| `type: reward` | `action: extract` |
| `type: any_of` / `random` | `flow: first_ok` / `pick_one` |
| `type: dismiss_popups` / `captcha` | `macro:` 同名 |
| `type: ensure` | 任意 step + `on_miss: fail` |
| `type: scroll_to` | `action: click` + `target.search: scroll` |
| 候选 `type: text` | `target.by: text` |
| `point` / `template` / `vlm` | 坐标走 `tap`/`fallback`；`template→image`；`vlm→vision` |
| `optional: true/false` | 见下 |

**`optional` 折算要分类，不能一刀切**（实测 237 处）：

- 在 `any_of` / `random` / `click_first` 上：**生效**（111 处）→ `on_miss: skip` / `fail`；
- 在 `click_text` / `click_id` / `click_desc` / `click_point` 上：**从来没被读过**（126 处，死字段）
  → 直接丢弃并 WARN。它们写不写，行为完全一样，折算成 `on_miss` 会**凭空改变行为**。

## 12 迁移路径

| 阶段 | 内容 | 配置改动 | 验收 |
|---|---|---|---|
| 1 | 别名层：编译层认 `action`/`flow`/`macro`/`target`/`on_miss`，`type` 继续可用 | 0 | 452 测试全绿；日志动词表锁进测试 |
| 2 | 清 `intent_map`（删 61 条恒等）+ `bonus/gift → chest` + 删 `open` | 增量 | 逐 App dry-run 语义投影一致 |
| 3 | 编译层 v1 `type` → v2 三维度 | 0 | **语义投影对拍**（见下） |
| 4 | `behaviors → routines` 双 key 兼容，逐 App 迁移 | 结构性 | 每迁一个跑一次 dry-run |

**对拍口径**：`--dry-run` 现在打印原始 YAML dict，编译后 schema 必然不同，
**"逐字相等"做不出来**。正确做法是编译前后各生成
`(维度, 值, by, selector, timeout, on_miss, vision, expect)` 元组序列再比对。

## 13 已知取舍

1. **`daily_report` 0 实现**：占位换架构完整；代价是补链前报告对 34 个 App 输出「日报：不支持」。
2. **`collect` 终态是结构判定**：没有单一目标，比其它意图更难自动验证。
3. **不做 recipe**：实测跨 App 复用仅 16 个模板、最多省 119 步（30.6%），前几名是
   `think`(31 App)/`swipe`(17)/`wait`(17) 这类单步，抽了也省不了维护成本。
4. **`chest` 名字略窄**：10 条里 4 条是红包/翻牌/抽奖，词表需写明"宝箱/红包/翻牌/抽奖/领取奖励"。
5. **`withdraw` 名实不完全一致**（见 §3.2），靠报告第四态「待人工」表达。
6. **保留 `any_of`/`random` 别名**：老配置不改，但两个名字并存需文档说清。
7. **顺序不强制 → 存量 99 条 routine 都没有终态检查**。这是 v6 引入的迁移成本：
   要让"先跑 collect 再跑 sign"安全，每条链都要补一个"先判终态"的入口步。
   这是本次改造里唯一需要逐 App 手写配置的部分。

## 14 待审问题

1. `collect` 作为"兜底意图"是否该降级为执行阶段？它没有单一目标，只有"扫干净了"。
2. `chest` 与 `collect` 在 5 个 App 里并存（快手/微博/飞猪/支付宝/红果），"具名容器 vs 扫页面"的划分是否有反例？
