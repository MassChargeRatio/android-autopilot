## 一、本轮要解决的主要矛盾

第二轮的结论是：**结果会波动，单轮 pass/fail 不算数**。同一批配置、同一台设备，
不同轮次结果差异显著（一淘.sign 三轮三种结果；火龙漫剧 3 个行为在
「全未命中 / 全导航后命中 / 全首屏命中」之间跳）。

根因不是锚点写错，而是 **App 落地页不确定**（开屏广告 / 活动弹窗 / 新手引导 /
上次退出的 tab / 登录态 / 灰度活动页）。由此推出两条结构性对策：

| 对策 | 内容 | 状态 |
|---|---|---|
| **A. `any_of` 条件动作** | 同一行为里让「首屏直连」和「导航后查找」两条路径共存，按顺序试，第一条命中即停 | ✅ 已实现并写回 31 处 |
| **B. 多轮稳定性度量** | 用「命中率 = 命中轮数 / 有效轮数」替代单轮 pass/fail | ✅ 工具已建（`stability_run.py`） |

## 二、`any_of`：从「写死一条路」到「多路径覆盖」

### 为什么写死前置步一定失败

第二轮的实测反例：给「锚点本来就在落地页」的行为加「先点我的」前置步后，
真实执行会**先跳走再找** → 必然失败（`remove_prelude.py` 已移除 1 处）。
而反过来，只写首屏锚点，页面一漂移就全灭。

### 实现

```yaml
    sign:
    - type: any_of
      optional: true
      choices:
      # 分支1：首屏直接找（optional 必须为 false，否则"没找到"会被当成成功）
      - - {type: click_first, candidates: [签到, 每日签到], optional: false}
      # 分支2：先跳「我的」再找
      - - {type: click_point, vlm_prompt: "...最右侧的『我的』...",
           x: 0.9, y: 0.915, vision: false, optional: true}
        - {type: think}
        - {type: click_first, candidates: [签到, 每日签到], optional: false}
```

关键语义（`executor._step_any_of`）：
1. 分支按顺序试，**该串全部动作都成功**才算命中，命中即停；
2. 分支内定位动作必须 `optional: false` —— 否则「没找到」返回 False 会被误判成功；
3. **只有最后一个分支允许触发视觉兜底**（`_probe_no_vision`）：
   前面的分支是"便宜的探测"，本机 VLM 图像请求常 90s 超时，
   若探测分支也走视觉，一次 `any_of` 可能白等好几分钟；
4. 全部分支未命中时按 `optional` 放行或抛 `StepError`。

`_dispatch` 同时改为**返回布尔**（`None → True`，`False → False`），
否则 `optional` 定位动作的「未命中」无法被上层识别。

## 三、跨 App 污染：判定源从「前台包名」改为「dump 自身」

**踩过的坑**：目标 App 启动失败/崩溃时，前台会停留在**上一个 App**，
于是两个 App 会得到**完全相同的坐标**（看似合理、实为垃圾数据）。
先加的 `d.info.currentPackageName` 前台校验**不够** —— 时序上它会先报新包名，
而屏幕上还是旧 App。

**新做法**（`calibrate.page_belongs_to`）：统计 dump XML 里各 `package` 属性的
节点数（排除 `com.android.systemui` 等系统包），取节点数最多者作为
「屏幕上实际是谁」，再判断目标包是否出现且不低于主导包的一定比例。

```
PKG_ATTR_RE = re.compile(r'package="([^"]+)"')
SYS_PKGS = {"com.android.systemui", "com.android.vivo.upslide", "android",
            "com.android.bbk.launcher2", "com.bbk.launcher2"}
def page_belongs_to(xml_text, pkg, ratio=0.5) -> (ok, dominant_pkg, mine, dom_n)
```

**验证**（对 34 份真实 dump 全量跑一遍，`tests/test_page_owner.py` 固化）：

| 结果 | 数量 | 说明 |
|---|---|---|
| 判为属于目标 App | 32 份 | 与预期一致 |
| 判为污染 | 2 份 | `天天快讯极速版` 的 ui.xml / ui_after.xml，主导包分别是 `com.vivo.doubletimezoneclock`（时钟）与 `com.vivo.gallery`（图库）—— 与第二轮"dump 实际抓到系统 App"的诊断完全吻合 |

已接入：`verify_live.py`（污染轮次标 `数据作废(页面非目标App)`，不计入分母）、
`probe_deep.py`（L1/L2/L3 三级都校验）、`calibrate.py`（报告标注 + 批量汇总提示）。

## 四、底部导航带：修掉「假命中」与「点错元素」

**踩过的坑**：`withdraw` 这类行为的第一步锚点就是 `我的` / `我`，
而页面**中部**也会出现同名标签。实测蛋花免费小说二级页命中过
`text='我的' @(575,627)` —— 1080×2340 的屏幕上 y=627 是页面中部，
不可能是底部导航栏（底部导航实测 y≈2100+）。这会造成两个后果：

1. **度量虚高**：把「找到页面中部一个『我的』标签」当成「找到了导航入口」；
2. **执行出错**：执行器可能真的点到页面中部那个标签。

**新做法**：目标词属于 `NAV_LABELS`（我的/我/首页/个人中心）时，
命中必须落在屏幕底部带（`y >= 0.80 × 屏高`）才算数，否则判「疑似假命中」。

- 校验侧：`verify_live.check_anchor(nodes, act, screen_h)`，`any_of` 分支继承该校验；
- 执行侧：`executor._pick_best` 对导航标签做**加分/减分偏好**（±120），
  **不做硬过滤**，避免误伤特殊布局。

> ⚠️ 由此得出一个重要的**口径提醒**：`withdraw` 的锚点是「我的」，
> 所以「withdraw 命中」只代表**找到了进入我的页的入口**，
> 不代表找到了提现入口。锚点层命中率是**上界**，不等于功能完整度。

## 六、导航步跳过视觉兜底（`vision: false`）

**问题**：`click_point` 只要带 `vlm_prompt`，执行器就会**先截屏 + 走 VLM**。
而导航「我的」是**每个行为都要执行**的固定步骤，本机 VLM 图像请求常 90s 超时
或返回 `User Safety: safe`（非确定性）—— 让它走视觉既慢又不稳。

**做法**：新增 `vision: false` 开关，导航前置步显式关闭视觉，直接用比例坐标
（已在 18 个 App 上验证：各 App『我的』中心 y 落在 2106~2192）。
保留 `vlm_prompt` 字段仅作**语义标注** —— devtools 靠它识别「这是导航前置步」。

已用 `devtools/patch_nav_vision.py` 幂等写回 **31 处**。

## 七、收益数字提取：从「整份 XML 取第一个匹配」到「按语义择优」

**踩过的坑**：原实现是 `re.search(pattern, xml)`，直接在**整份 UI XML** 上取第一个
匹配。页面上的活动横幅（如「新人专享1元」）、广告位数字都会被当成账户余额，
收益表里记的就是横幅数字。

**新做法**（`executor._reward_candidates`）：
1. 只在 `text="..."` / `content-desc="..."` 属性值里找（不再扫 resource-id / bounds）；
2. 多处匹配时，金额类（`unit=元`）优先取带
   `可提现/提现/余额/钱包/现金/账户/收益` 语义的文案；
3. 配置里给了 `context` 关键词时，context 优先级最高；
4. 属性里一处都没有时，退化为整份 XML 兜底（兼容跨标签的旧 pattern）；
5. 多处匹配时在日志里标注「页面有 N 处匹配，取 X」。

## 十二、⚠️ 本轮最重要的发现：两个「看起来对」的缺陷

### 12.1 `check_anchor` 把三级分支的**中间入口**当成命中

三级 `any_of` 分支形如：

```
[ 我的, think, 福利中心, think, 签到 ]
                  ↑中间入口        ↑目标锚点
```

中间入口「福利中心」**也是锚点类动作**。早期 `check_anchor` 的实现是
「分支里任一锚点动作命中即算该分支命中」，于是落地页上只要有「福利中心」，
就报成 `首屏命中 any_of 分支#2: text='福利'`。

后果：**3 个三级 sign 行为的命中全是假的**，而且假得"很像真的"
（有具体文案、有具体坐标）。若不做交叉核对（明细里的文案与目标锚点对不上），
会直接把假数据当成成果汇报。

**修正**：一个分支是否命中，取决于该分支的**最后一个**锚点动作（真正的目标）。
已用 `tests/test_anchor_anyof.py` 钉死（含"中间入口单独出现不算命中"的反例）。

**顺带发现**：`convert_deep` 生成的两条分支**共用同一个目标锚点**，
所以单份 dump 上分支2 不会比分支1 多命中 —— 分支2 的价值在于
「换一个页面再找」，必须靠**真的把分支走完**才能验证（见 12.3）。

### 12.2 `_probe_no_vision` 只在 `any_of` 里赋值，却被 4 处直接读取

`any_of` 需要「只有最后一个分支允许视觉兜底」，靠 `self._probe_no_vision` 控制。
但它最初**只在 `_step_any_of` 内部赋值**，而
`_step_click_text/_click_id/_click_desc/_click_first` 里是**直接读取**。

后果：**任何不含 `any_of` 的行为**（34 个 App 里大量存在）一旦走到
「元素没找到 → 该走视觉兜底了」这一步，就会
`AttributeError: 'Executor' object has no attribute '_probe_no_vision'`
—— 把「按钮没找到」这种正常情况变成**崩溃**。

**修正**：在 `__init__` 里给默认值；`tests/test_probe_flag.py` 钉死
（含"删掉该属性就会崩"的反证用例，证明测试真的抓住了缺陷）。

**排查方法**（可复用）：用 AST 扫「`__init__` 未初始化、且只在一处赋值
但被多处读取」的实例属性。本项目扫描结果：仅 `_probe_no_vision` 一处真实问题
（其余命中项都是方法/类属性，属误报）。

### 12.3 `verify_live` 只走一步，无法验证三级路径

原验证器只做「启动 → 首屏 → 点我的 → 二级页」。对三级行为，
二级页（「我的」）上当然没有签到锚点 —— 必然判未命中，是**假阴性**。

**修正**：验证器识别出 `any_of` 分支里的中间入口后，会**继续点它并 dump 三级页**
再校验，即真的把配置里的路径走完。新增 `mid_entry_of` / `target_anchor_of` /
`find_anchor_node` 三个纯函数（均有单测）。

> 这三个缺陷有一个共同点：**都只在"真的按配置走一遍"时才暴露**。
> 只做静态检查或只看汇总数字，永远发现不了。

## 十三、⚠️ 修复后总分下降：不是改动变差，是它暴露了下一个缺陷

§11.2 显示"修完中间入口，总分从 69.9% 掉到 67.9%"。逐项回退里最刺眼的是
**喜番免费短剧 watch：3/3 → 0/3**。查完整执行日志后真相很清楚。

### 13.1 根因：行为之间不复位，App 被留在二级页

```
# 修复前（sign 首屏就命中，没导航，App 停在落地页）
  sign: 首屏命中 any_of 分支#2: text='赚现金' @(496, 2111)
  watch: 第1轮导航后 命中 any_of 分支#1: text='去看剧' @(968, 700)      ← 3/3

# 修复后（sign 走完三级导航，App 停在「签到」二级页）
  sign: 第1轮三级页 命中 text='签到' @(188, 1993)                       ← 修对了
  watch: 第1轮导航后页面不属于目标 App（主导包 com.eggflower.read）-> 作废
  watch: 第2轮导航后页面不属于目标 App（主导包 com.eggflower.read）-> 作废
```

`com.eggflower.read` 是**蛋花免费小说**，序列里排在喜番**前一个**的 App。
链路是：

1. `sign` 三级导航把喜番停在「签到」二级页（页面底部没有 tab 栏）；
2. `watch` 从脏页面起步，比例坐标兜底点 (972,2141) —— 那是**顶层页**「我的」
   的位置，在「签到」页上落到别的东西上，跳去了蛋花；
3. `page_belongs_to` 正确抓到「页面不是目标 App」→ 该轮作废 → 但计入分母时
   被记成**未命中**（见 13.2），于是分数掉了。

**所以这不是波动，是可复现的确定性缺陷**，而且**执行器里同样存在**：
`executor.py::run_app_flow` 是「一个 App 只 `_open_app` 一次，然后行为串行执行」
（L151→L164），第 N 个行为留下的页面会污染第 N+1 个。

### 13.2 两个缺陷

**(a) 行为之间不复位（验证器 + 执行器都有）**

修复：两边都加「复位到顶层页」，并**共用同一份判据**（新建 `ui_page.py`）：

- 先按 BACK（快、不触发开屏广告），每次校验前台仍在目标 App；
  一旦发现已离开目标 App 立刻停手改走重启 —— 开屏广告期继续按 BACK 会退出 App；
- 退不回去 → `app_stop` + `app_start` + `wait_ready`（确定但慢）；
- 只对**导航过**的行为复位（首屏命中 = 没离开顶层页 = 不用复位），省掉大量重启；
- 「顶层页」判据刻意做硬：底部带里 **≥2 个不同 tab 名**，或出现
  `首页/推荐/我的` 之一。只用"底部有没有某个词"会被二级页的同名文字骗过。

**(b) 作废轮次与统计口径脱钩**

验证器打了 `-> 本轮作废`，`stability_run.py` 的 `is_void()` 只认
`数据作废` 前缀，而这个分支当时**照常输出"导航后仍未命中"** ——
于是「测量无效」被记成「没命中」，**系统性低估命中率**。

修复：两轮导航都落在别的 App 上时输出
`数据作废(导航后页面非目标App)`，前缀契约与 `is_void()` 对齐，并加单测锁死。

### 13.3 方法论：怎么区分「改动变差」和「波动」

这次差点得出反向结论。判定顺序应该是：

1. **看回退项有没有共同结构**。这里 3 个回退项全部是「排在导航型行为之后」的，
   不是随机分布 —— 随机波动不会这么整齐。
2. **拉完整执行日志**，不要只看汇总。汇总只说"未命中"，日志说
   "页面不属于目标 App（主导包 com.eggflower.read）" —— 后者直接指出根因。
3. **能复现 → 是缺陷；多跑几轮会翻转 → 是波动**。前者必须修，后者别动。

> 一句话：**总分下降不一定是改错了，可能是改对了之后，把原来被掩盖的问题顶出来了。**

### 13.4 修复效果验证

**针对性验证**（单 App 实跑，`verify_live.py --apps 喜番免费短剧 --probe-nav --nav-fast`）：

```
  sign    导航后命中  （三级页）text='签到' @(539, 702)
  watch   导航后命中  text='去看剧' @(968, 700)     ← 与 11.1 同坐标，不再点飞到蛋花
  withdraw 导航可救   text='我的' @(970, 2145)
```

**全量验证**（3 轮 × 18 App × 52 行为，见 §11.3）：110/156 = **70.5%**，
回退项全部恢复，作废轮次 0，从未命中 15 → 14。

**产品侧同步修复**：`executor.py::run_app_flow` 也接入了同一套复位，
`tests/test_executor_reset.py`（5/5）锁住"3 个行为 → 2 次复位"的接线，
并验证 dry_run 下不触碰设备、`ui_page.py` 缺失时优雅降级。

**遗留优化（未做，避免再动已验证的代码）**：27 次 BACK 全部以重启收场，
单批次多花约 10~15 分钟。可考虑改为「优先点 App 自己的首页 tab」，
或把 BACK 后的"退出确认对话框"识别出来并取消。**属于性能优化，不影响正确性。**
