### 1.1 这个项目是什么

一句话：**用 Python + uiautomator2 在真机上模拟真人，把「签到 / 看视频 / 提现」这类每日任务跑完。**

用户输入是一句自然语言，例如：

```bash
python main.py --task "去趣头条签到，然后看视频，最后提现"
```

程序会：解析出 `[sign, watch, withdraw]` 三个意图 → 找到「趣头条」的配置 → 依次执行该 app 在
YAML 里写好的步骤链（点击/滑动/等待/分支/坐标点击/视觉兜底/收益识别）→ 记录日志与收益。

设计上刻意做了两件事：

1. **配置驱动，运行期零 app 特判。** 34 个 app 的差异全部在 `config/apps/*.yaml`，没有任何
   `if app == "拼多多"` 这类代码。加一个新 app = 加一个 YAML 文件。
2. **像人。** 点击带抖动、动作间有随机停顿、滑动走贝塞尔轨迹而不是直线、会随机"分心"乱逛、
   有作息时间窗、同一行为有多套候选模板随机切换（避免每次路径一模一样被风控识别）。

它不是爬虫，不是 RPA 录制回放，也不追求通用性：**只服务这台设备上的这 34 个 app**。

### 1.3 架构一页图

```
CLI (main.py)
  │  --task "去XX签到并看视频"
  ├─ nlu.parse_intents()        自然语言 → [(sign,'签到'), (watch,'看视频')]
  ├─ nlu.match_app()            名称/别名/包名/序号 → app 配置（六级收窄，防"京东理财"被"京东"抢走）
  └─ config_loader.load_config() 合并 config.yaml + config/apps/*.yaml → apps[]
        │
        ▼
Executor(app_cfg, intents)                      ← executor.py，109 行门面
  ├─ DeviceSession   device_session.py   连接 / 冷启动 / 等页面稳定 / 回顶层 / 安全 dump
  ├─ Locator         locator.py          定位四级降级 + 元素知识库 + 视觉兜底
  └─ BehaviorRunner  behavior_runner.py  顶层流程 / 分派 / 19 个 step 原语 / 收益识别
        │
        ├─ human.py           拟人：抖动、停顿、乱逛、误触回退、限流长停
        ├─ human_trajectory.py 手势轨迹注入（贝塞尔 + 变速 + 过冲）
        ├─ vision.py          模板匹配 + VLM（多模态模型输出归一化坐标）
        ├─ knowledge.py       元素知识库：selector 失败轮换 alternatives，连败 3 次置 disabled
        ├─ landing.py         点击后落地校验（5 信号投票：节点/模板/phash/结构/OCR）
        ├─ candidates.py      候选词表自搜寻（"按钮名称的共性"）
        └─ recorder.py        结构化日志（唯一成功判定的事实来源）
```

**定位的四级降级**（`locator._locate` 到 `behavior_runner._vision_or_miss` 的链路）：

```
① 元素知识库候选  →  ② uiautomator2 selector  →  ③ 多候选自搜寻 click_first  →  ④ 视觉兜底（模板 / VLM）
                                                                                    ↓ 都失败
                                                                            ⑤ 比例坐标盲点（click_point，可配 expect 校验）
```

**执行一次行为的时序**：`run_app_flow` → 每个意图 → `_resolve(intent)` 得到 behavior 名 →
时间窗门控 → `_pick_variant` 选模板 → 逐步 `_dispatch_step`（前置 delay + 可能乱逛）→
`_run_kind` 按 type 分派 → 单步失败只记 WARN 并 `human.think()`，**不中断后续意图**。

### 1.4 请把这几条当"契约"看（评审时判断是否成立，而不是判断是否符合你的习惯）

| # | 不变量 | 为什么 |
|---|---|---|
| C1 | 单步未命中返回 `False`，不抛异常；只有 `ensure` / `captcha` / `swipe 缺坐标` / `scroll_to 无果` 抛 `StepError` | 一条链里某步 miss 很常见（弹窗/灰度/网络），抛异常会让整个 app 白跑 |
| C2 | 视觉兜底由**参数链** `allow_vision` 显式门控，不用实例标志位 | 早期用实例标志位"临时改写再还原"，异常后留下脏状态 |
| C3 | 配置里的 behavior 名必须是 `^[a-z][a-z0-9_]*$` 的 ASCII | 中文 behavior 名无法被任何意图命中，只能靠 intent_map 手写映射，形同虚设 |
| C4 | `intent_map` 只做「意图 → behavior 名」重命名，不改变语义 | 抖音火山版没有签到只有预约：`intent_map: {sign: reserve}`，用户说"签到"能跑，但行为名不撒谎 |
| C5 | 老 step 名（`click_text/id/desc`、`swipe_natural`）永久保留为别名 | 34 个 app 的 541 步是实机验证过的，不做批量改写 |
| C6 | 资金类动作有红线：弹窗清扫命中「提现/支付/银行卡/实名」等文案即熔断并禁用 BACK；提现链只走到「看到余额」为止 | 跳过用户确认 = 踩资金二次确认红线 |
| C7 | 「签到成功」的判定**只看点击凭据**（`sign_evidence.py`），不看"跑完了""GREEN""金币变多" | 用户 2026-10-25 定的口径，见下节 |

### 1.5 本轮改动（2026-10-25）：behavior / type 两层整理 + 签到判定规则

#### 1.5.1 用户新增的判定规则

> **只有复核过「签到按钮确实被点过了」，才认为已经成功签到。**

落地为 `sign_evidence.py`（`第 2 册 §2` 全文）。认可的凭据只有两类：

- **点击凭据**：日志出现「多候选命中并点击 / 点击文本 / 视觉兜底点击成功」之一，
  且该行文案命中签到词表（签到、立即签到、签到领取、领金币、领现金、开宝箱…）。
- **终态凭据**：重开 app 看到已签状态（已连续签到 N 天 / 今日格 ✓），由调用方离线核验。

**故意不认**：任务执行完毕、体检 GREEN、日志里没有"步骤失败"、顶部金币计数、
盲点 `点击坐标: (x,y)`、导航入口（任务/任务中心/赚钱/我的）。

#### 1.5.2 整理前发现的 8 个真实缺陷（全部有实机或日志证据）

| # | 缺陷 | 影响 |
|---|---|---|
| P1 | `click_text/id/desc` 是同一段 20 行代码的三份拷贝 | 改一处忘两处：B6「未命中不抛 StepError」当年只打进 `click_text` |
| P2 | `swipe` 写 `natural: true` 时**忽略 from/to** 且永远向下滑 | 抖音火山版想"上滑回顶"，结果连滑到底，预约行被推得更远 |
| P3 | behavior 名出现中文（快手「白拿礼物」） | 任何标准意图都命中不了，intent_map 形同虚设 |
| P4 | `reserve`/`growth` 意图定义了但没有任何 app 用 | 意图层与行为层脱节 |
| P5 | NLU 关键词「签到领」挂在 `growth` 下 | 长词优先，把「签到领金币」解析成 growth 而不是 sign |
| P6 | `nlu.resolve_behavior` 与 `Executor._resolve` 逐行相同且无人调用 | 两份相同逻辑必然漂移 |
| P7 | `behavior_runner.py` 模块 docstring 抄了一份失效行号索引 | 代码三次搬迁后行号全错，误导定位 |
| P8 | 体检脚本用 `"sign" in behaviors` 选目标 | 用 `intent_map` 把 sign 映射到别名的 app（抖音火山版）被静默漏检 |

#### 1.5.3 修法

- 新增 `_step_click(by=text/id/desc)` 一份实现；旧三名改为一行别名；`_CLICK_KINDS` 表驱动。
- `_step_swipe` 改为：有 from/to → 按坐标走轨迹；无 from/to → 保留随机自然滑动（录制流语义）。
- `nlu.py` 删死代码、growth 删「签到领」、新增 `gift` 意图、正式启用 `reserve`。
- 抖音火山版 behavior `sign` → `reserve`，配 `intent_map: {sign: reserve}`。
- 体检脚本 `targets()` 改按 intent_map 解析。
- 新增 26 条回归（`test_sign_evidence.py` 12 + `test_unified_steps.py` 14）。
- **541 步老配置一行未改，行为零变化**；回归门 `422 passed` + 行为覆盖率 99/99。

### 1.6 想请你回答的问题（按优先级）

#### P0 —— 直接影响正确性

**Q1「签到成功」的判定方式是否站得住？**
`sign_evidence.py` 靠"日志行 + 词表子串"判定。我担心的具体漏/误：

- 词表里 `福利`、`领金币` 过宽：点中「福利中心」入口、点中「领金币」任务行，都会判成签到成功；
- 词表里 `签到` 是子串匹配：点中「签到规则」「签到日历」「补签」也会命中；
- 只认三条日志动词：若某天 `click_first` 换了措辞（如改成「候选命中」），判定会**静默全灭**（不报错，只是全部变"未确认"）。

请判断：这套判定的误报率/漏报率哪个更危险？如果要加"终态复核"（重开 app 看已签状态），
最小可行实现是什么？是否有更好的证据来源（页面结构断言 / 收益变化 + 基线 / 网络层）？

**Q2 有没有更结构化的"成功"载体？**
现在所有判定都从日志文本里 grep，本质是把日志当数据库用。迁移到「结构化事件流 + 断言」的
成本/收益如何？在**不重写 541 步配置**的前提下，能否只改 `recorder` 与 `sign_evidence` 的边界？

#### P1 —— 设计层面

**Q3 三重多继承门面 + `self._xxx` 可覆盖入口，这个取舍合理吗？**
`Executor(DeviceSession, Locator, BehaviorRunner)`，方法体内互相调用走 `self._xxx`，为的是让
测试能对实例打桩（`ex._locate = fake` 在 MRO 上优先）。代价是：MRO 隐式、方法归属靠 grep、
IDE 跳转不准、`_extras_cache` 这类实例属性散落在 mixin 里。有没有既保住 422 个测试、又能让
依赖关系显式的方案？（组合 + 显式委托？协议类？构造注入？）

**Q4 15 种 step 类型、541 步 YAML，是否已到 DSL 的复杂度临界点？**
现在的类型是"原语"（click/swipe/wait/any_of/click_first/click_point/reward/ensure…），
组合方式是嵌套 list。缺的是：变量/参数化（同一套链路 34 个 app 抄 34 份）、循环、显式错误处理、
schema 校验（现在只有 `validate_config` 的轻量检查）。你会先补哪一项？还是说这个规模就**不该**上 DSL？

**Q5 测试的"假绿"风险怎么防？**
422 个用例里大量 mock 掉 u2 device，跑得很快但测的是"逻辑分支"不是"真机行为"。
更具体的风险：cv2 / PyYAML 缺失时整套能力静默降级（`executor.py` 里 5 个 `try/except ImportError`），
于是测试用错解释器会红 4 个、线上用错环境会静默退化。请评估：这些降级分支值不值得保留？
如何在启动时"快速失败"而不是静默降级？

#### P2 —— 工程与效率

**Q6 校准效率。** 每个 app 的链路是人工跑 `devtools/probe_*.py` 十几轮试出来的（配置注释里留着
"旧值 0.5/0.18 偏左错过"这类记录）。有没有可能做出"半自动校准闭环"：给定目标文案 → 自动探测
可达路径 → 生成候选步骤 → 实机验证 → 回写 YAML？最小可行版本长什么样？

**Q7 风控与合规边界。** 反检测手段（抖动/轨迹/乱逛/限流长停/多模板随机）在
`docs/ANTI_DETECTION.md` 有威胁面分析。资金类动作只到"看到余额"。这个边界设计有没有明显漏洞？

### A 类：会让判定结果失真的（最危险）

#### A1 「签到成功」判定依赖日志措辞，措辞一改就静默全灭

- **证据**：`sign_evidence.py: CLICK_LINE` 只匹配三条动词——「多候选命中并点击」「点击文本」「视觉兜底点击成功」。
- **现象**：如果 `click_first` 的日志改成「候选命中」、或 `_step_click` 的动词表 `_CLICK_KINDS` 改了措辞，
  所有 app 会**静默**变成"未确认"——不报错、不告警，只是报告里全部 ❌。
- **影响**：判定系统失效时没有任何信号，比判错更糟。
- **我倾向**：把"日志动词"收进一个常量表，由 `sign_evidence` 与 `recorder` 共用；再加一条自检用例
  （跑一次 dry-run，断言至少产出一条可识别凭据）。
- **要你判断**：这个自检够不够？还是应该让 `recorder` 在写日志时就带上 `event=click_hit` 这类结构化字段？

#### A2 词表过宽 + 子串匹配 → 误报

- **证据**：`SIGN_WORDS` 含 `福利`、`领金币`、`签到`；匹配方式是 `w in line`。
- **具体误报路径**：
  - 点中「福利中心」入口 → 命中 `福利` → 判成功；
  - 点中任务列表里「领金币」的**任务行**（不是签到按钮）→ 判成功；
  - 点中「签到规则」「签到日历」「补签」→ 子串命中 `签到` → 判成功。
- **影响**：误报比漏报更危险（会让人以为今天签到了，实际没签）。
- **我倾向**：把词表分两档——**强证据**（立即签到/签到领取/每日签到/金币签到）与**弱证据**（签到/福利/领金币），
  强证据直接判成功，弱证据要求同一行同时出现"按钮类动词"或配合 `expect` 落地校验通过。
- **要你判断**：分档是不是把问题复杂化了？有没有更简单的判据（比如只认"签到"前面没有"规则/日历/补签"这类否定前缀）？

#### A3 GREEN 但无凭据的三个 app

- **证据**：体检报告里 河马剧场 / 火龙漫剧 / 飞猪旅行 三条链路 GREEN，但日志无任何点击凭据。
- **可能原因**（未验证）：① 签到入口是纯图标，只能盲点坐标；② 签到在二级页，链路实际没走到；③ 这三个 app 的签到按钮文案不在词表里。
- **影响**：这是"看起来在跑、其实没签到"的典型样本，也是判定规则存在的意义。
- **要你判断**：应该先补终态凭据（重开 app 看已签状态）还是先补点击凭据？哪个投入更小？

#### B2 7 个 YELLOW（落地校验/锚点对不上）

- **共性**：`expect` 里的 phash 参考图与当前页面 dHash 距离超阈值 → 说明页面皮肤/布局变了。
- **我倾向**：YELLOW 不一定要立刻修——链路能跑完，只是校验对不上。**但如果校验长期对不上，

- **要你判断**：`expect` 校验失败应该算 YELLOW（现状）还是直接算 RED？还是按"连续 N 次失败"升级？

#### B3 全民K歌没有 `sign` 行为

34 个 app 里唯一一个没配 sign 的（只有 `open`/`watch` 之类）。从未实机校准过。
**判断**：是补链路，还是承认它不支持签到、从 sign 目标里剔除？
