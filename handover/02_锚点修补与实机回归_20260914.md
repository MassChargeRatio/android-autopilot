## 2.5 ⚠️ 最重要的结论：结果波动

同一批配置、同一台设备，**不同轮次结果差异显著**：

| 行为 | 第 1 轮 | 第 3 轮 | 第 4 轮（最终） |
|---|---|---|---|
| 一淘.sign | 首屏未命中 | 导航后命中 | 未命中 |
| 一淘.watch | 导航后命中 | 未命中 | 导航后命中 |
| 火龙漫剧.sign/watch/withdraw | 全部未命中 | 全部导航后命中 | 全部首屏命中 |
| 喜番免费短剧.watch | 导航后仍未命中 | 未命中 | 导航后命中 |
| 河马剧场.withdraw | 首屏未命中 | 首屏命中 | 首屏命中 |
| 全民K歌.collect | 未命中 | 首屏命中 | 首屏命中 |

**根因**：App 启动后的落地页不确定 —— 开屏广告、活动弹窗、新手引导、
上次退出的 tab、登录态、灰度活动页都会改变落地页。
**锚点本身没错，是页面不确定。**

**推论**
1. 单轮 pass/fail 不足以判定锚点好坏，**必须多轮统计命中率**。
2. 配置应追求**多路径覆盖**，而不是单点最优。
3. 需要一个「先把 App 带到确定页面」的前置动作，结果才能复现。
4. **建议给 executor 加 `any_of` 条件动作**（按顺序试多组动作，第一组成功即停），
   从根上消除「前置步堵死首屏路径」与「首屏偶尔无锚点」两类失败。
   详见 `devtools/calib/ROUND2_FINAL.md` §五。

## 3. 关键方法论发现 ⚠️

### 3.1 离线 dump ≠ 实机真值
`河马剧场.withdraw` 离线分析判 `keep`（"首屏已命中 text=我的"），
**实机却未命中**。原因：早期校准的 `ui.xml` 只是「某次会话的页面快照」，
会随弹窗、新手引导、登录态、活动页漂移。

> **铁律：锚点分类以 `verify_live.py` 的实机结果为准，dump 只当线索。**

### 3.2 校准工具必须校验前台包名
`天天快讯极速版` 的早期 `ui_after.xml` 实际是**系统「图片」App**的界面
（底部 tab：图片/相册/推荐/搜索）——目标 App 从未进入前台，
却产出了"看起来合理"的锚点数据。
`今日看点极速版` / `全民K歌` 的二级页 dump 则是**奖励弹窗 / 全屏广告**。

→ `calibrate.py` 应增加「前台包名 ≠ 目标包 → 直接判失败」，
并补充奖励弹窗/开屏广告的关闭按钮文案。

### 3.3 抖音系的入口在两级菜单之后
`抖音`/`抖音极速版`/`抖音火山版` 的「我的」是**纯个人主页**，无金币/任务入口；
入口在右上角 `≡ 更多`（`desc='更多'` @(984,174)）展开的**侧边栏**里。

**好消息：不需要改架构。** `config.yaml` 的行为本来就是动作列表，
直接写两步 `click_point` 即可：

```yaml
    watch:
    - type: click_point
      vlm_prompt: "定位屏幕底部导航栏最右侧的『我』标签中心"
      x: 0.9
      y: 0.915
      optional: true
    - type: think
    - type: click_point
      vlm_prompt: "定位屏幕右上角的『更多』汉堡菜单按钮（三条横线）中心"
      x: 0.911
      y: 0.074
      optional: true
    - type: think
    - type: click_first
      candidates: [ ... ]
```

### 3.4 纯图标按钮要用 `click_id`
`click_first` 的候选支持 `type: id`（`executor._locate` 走 `resourceId` **精确**匹配）。
河马剧场「我的」页顶部 5 个图标 `text`/`desc` 全空，但 rid 齐全：

| rid | 语义（目视确认） |
|---|---|
| `item_message` | 消息 |
| `item_wallet` | **福利**（签到入口） |
| `item_cash` | **提现** |
| `item_mall` | 我的商城 |
| `item_reservation` | 预约 |

### 3.6 前置步不是越多越好 ⚠️
若某行为的锚点本来就在**落地页**，又给它加了「先点『我的』」的前置步，
真实执行时会「先跳到我的页 → 再找只有落地页才有的锚点」→ **必然失败**。

实测 `今日看点极速版.sign`：锚点 `签到` 在第 1 轮出现在**首屏**，
第 3/4 轮在两页都未出现（从不在二级页）。加了前置步后，
首屏那条路径被彻底堵死 → 已用 `devtools/remove_prelude.py` 移除。

> 工具：`remove_prelude.py --list` 可审计所有带前置步的行为。

| 工具 | 作用 |
|---|---|
| `plan_anchor_fixes.py` | 读 dump 分类锚点（keep/prelude/candidate/rid/manual），`--apply` 幂等插入前置步；支持 **rid 语义扫描** |
| `apply_candidate_fixes.py` | 把实测文案写入 `click_first.candidates` 首位（已用 12 处） |
| `apply_nav_fixes.py` | 消费实机探路 JSON，自动补前置步（已用 2 处） |
| `remove_prelude.py` | **移除**有害前置步 + `--list` 审计（已用 1 处） |
| `verify_live.py` | **实机锚点回归**；`--probe-nav` 对所有未命中项试导航；`--nav-fast` 跳过 VLM 加速；**前台包名校验** |
| `probe_manual.py` | manual 项 VLM 探针 + 截图存盘供目视复核 |

### 本轮工具踩坑（都已修）
1. **状态判定写反**：`导航可救` 条件最初写成 `hit2=False and not prelude`，
   应为 `hit2=True and not prelude`，导致整轮状态标签全部反了。
2. **跨 App 污染**：目标 App 启动失败时前台停留上一个 App，
   两个 App 会得到**完全相同的坐标**（看似合理、实为垃圾数据）。
   已加**前台包名校验** + 启动重试；校验最终失败直接判「数据作废」。
3. **rid 启发式误报**：`kw in rid` 把点淘 `tl_home_capture_video_btn` 误判成
   看视频入口。收紧为「剥离 `item_/btn_/iv_...` 前缀后**以关键词开头**」。
4. **VLM 图像请求不稳定**：本机网关**文本**请求 3~12s 正常，但**图像**请求
   常 90s 超时或返回 `User Safety: safe`。一次导航可能耗 9~27 分钟
   → 跑批用 `--nav-fast` 走比例坐标（已验证可靠）。
5. **重定向到文件时 Python 会缓冲**：跑批加 `-u` 才能实时看进度。

### rid 扫描的教训
初版用 `kw in rid` 匹配，把点淘的 `tl_home_capture_video_btn` 误判成看视频入口。
收紧后 rid 命中降为 0 —— 说明纯启发式收益有限，`item_wallet=福利` 这类
语义仍需人工/视觉判断。
